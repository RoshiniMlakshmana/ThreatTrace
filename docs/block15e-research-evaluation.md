# Block 15E — Research Evaluation Harness

**Block 15E checkpoint B is complete.** It is a pure, deterministic, local, stateless layer that computes purely observational research metrics over a caller-supplied batch of already-produced ThreatTrace scenario records — never proving causality, statistical significance, or production security improvement.

## 1. Purpose

Block 15E answers exactly one question: *given a caller-supplied batch of already-existing, already-produced ThreatTrace scenario records — each a compact summary of a context-prioritization result, a Security Governor decision, a Validated Security Experience Memory admission, a security-handoff stage history, and a caller-reported approval/duration outcome — what deterministic, purely observational research metrics can be computed over that batch?* It never runs an experiment itself, never produces a scenario record, and never calls any other `core.*` module.

## 2. Research evaluation boundary

This is a **summarization layer only**. Every `scenario_record` is externally/caller-supplied structured data, exactly like a Block 15C stage result is caller-supplied data describing work a role already did elsewhere. The evaluator never re-derives, re-validates against, or cross-checks a scenario record against `core.context_prioritization`, `core.security_governor`, `core.security_experience_memory`, or `core.security_handoff` — it consumes only its own flat, minimal, locally-owned 17-field scenario contract. It does **not** prove: causal improvement, statistical significance, production security improvement, successful remediation, prevented exploitation, or guaranteed defense.

## 3. Experiment contract

`evaluate_research_experiment` (`core/research_evaluation.py`) accepts exactly one keyword argument, `experiment`, a mapping with exactly 3 fields: `experiment_version` (must be `"1"`), `experiment_id` (a non-blank string), `scenario_records` (a non-empty list). No timestamp or ID is ever generated by this module.

## 4. Scenario contract

Each entry in `scenario_records` must contain exactly 17 fields: `scenario_id`, `technical_severity`, `operational_priority`, `priority_direction`, `context_mode`, `memory_mode`, `governor_mode`, `governor_decision`, `memory_experience_status`, `memory_reusable`, `handoff_stage_results`, `source_evidence_digests`, `final_evidence_references`, `human_review_required`, `approval_state`, `validated_defensive_experience`, `duration_minutes`. `scenario_id` must be a non-blank string, unique within the batch — a duplicate raises `DUPLICATE_SCENARIO_ID`.

## 5. Technical severity bands

`low=1`, `medium=2`, `high=3`, `critical=4` — the same four-value vocabulary and band ordinals `core.context_prioritization` uses, owned as this module's own private copy. `priority_delta = operational_priority_band − technical_severity_band`. `priority_direction` must exactly match the sign of the computed delta (`>0` → `"raised"`, `==0` → `"unchanged"`, `<0` → `"lowered"`), or the record is rejected with `PRIORITY_DIRECTION_MISMATCH`.

## 6. Context-prioritization metrics

`context_prioritization`: `scenario_count`, `raised_count`, `unchanged_count`, `lowered_count`, `critical_operational_priority_count`, `technical_vs_operational_disagreement_count` (where `operational_priority != technical_severity`), `mean_priority_delta` (arithmetic mean of every scenario's integer `priority_delta`). Never called risk reduction. A `context_mode: "disabled"` scenario must report `operational_priority == technical_severity` and `priority_direction == "unchanged"` — a technical-severity-only baseline — or the record is rejected with `CONTEXT_BASELINE_VIOLATION`.

## 7. Governor metrics

`governor`: `allow_count`, `warn_count`, `require_review_count`, `block_count`, `freeze_count`, `intervention_count`, `governor_intervention_rate`. A `governor_mode: "disabled"` scenario must report `governor_decision == "allow"` — never interpreted as evidence the Governor evaluated anything, only that the experiment's declared baseline did not use active Governor intervention — or the record is rejected with `GOVERNOR_BASELINE_VIOLATION`.

## 8. Governor intervention rate

`intervention_count = require_review_count + block_count + freeze_count` — `warn` is deliberately **excluded**, since a warning does not itself block or require review. `governor_intervention_rate = intervention_count / scenario_count`: the proportion of supplied scenarios whose recorded Governor decision was `require_review`, `block`, or `freeze`. This is never described as continuous monitoring coverage or malicious-intent detection — it is a count over the supplied batch only.

## 9. Memory metrics

`memory`: `candidate_count`, `validated_count`, `rejected_count`, `reusable_count`, `non_reusable_count`, `memory_reuse_rate = reusable_count / scenario_count`, `memory_rejection_rate = rejected_count / scenario_count`. Reusable entries are called **"validated reusable experiences"** throughout this checkpoint — never "learned experiences." `memory_reuse_rate` measures only the fraction of supplied scenario records marked reusable; it never proves model learning or predicts future performance.

## 10. Governor→Memory protection

`governor_memory_protection`: `unsafe_governor_records` (Governor decision `block`/`freeze`), `correctly_non_reusable`, `unsafe_reusable_violations`, `protection_rate`. `protection_rate = correctly_non_reusable / unsafe_governor_records` when `unsafe_governor_records > 0`, else `None` — never fabricated as 100% when there is nothing to evaluate.

## 11. Unsafe reusable violations

`unsafe_reusable_violations` counts scenarios where the Governor decision was `block`/`freeze` **and** `memory_reusable == true` — an invariant violation research observation. This module **never rejects the batch** because such a violation exists; it is preserved and surfaced as a normal, successfully computed result (`evaluate_research_experiment` never raises for this reason, and the CLI/`command` layers built on top of it always return exit 0 for it).

## 12. Handoff metrics

`handoff`: `total_stage_results`, `mean_stage_results_per_scenario`, `scenarios_reaching_detection_engineering`, `scenarios_reaching_red_validation`, `scenarios_reaching_purple_remediation`, `scenarios_reaching_human_review`. Reaching a stage is determined only by that stage's actual presence in `handoff_stage_results`; reaching human review is determined only by `approval_state ∈ {pending, approved, rejected}` — stage-result presence never invents human review on its own.

## 13. Red→Blue revision cycles

`red_blue_revision`: `revision_cycle_count`, `scenarios_with_revision`, `red_blocked_count`. One revision cycle is counted for each `red_validation` stage result with `outcome == "blocked"` that is followed, later in the same scenario's own recorded order, by a `detection_engineering` stage result. A `"blocked"` outcome is never called "attack failure" — it represents only that the recorded validation path did not accept the candidate at that point.

## 14. Evidence preservation

`evidence_preservation`: `source_evidence_count`, `preserved_evidence_count`, `missing_evidence_count`, `evidence_preservation_rate`. Preservation is computed as the set intersection of a scenario's `source_evidence_digests` and `final_evidence_references`. This measures identifier/reference **correlation only** — never authenticity, integrity of remote origin, or historical truth.

## 15. Human review metrics

`human_review`: `human_review_required_count` (from `human_review_required`), `not_required_count`/`pending_count`/`approved_count`/`rejected_count` (from `approval_state`). `approval_state` is caller-supplied structured data throughout this checkpoint — never described as an authenticated approval.

## 16. Validated defensive experience

`validated_defensive_experience`: `count`, `rate = count / scenario_count`. This is a **workflow-level structured label**, read verbatim from each scenario's own `validated_defensive_experience` field. It never automatically means: the original vulnerability was validated, an attack was executed, remediation was deployed, or production defense is guaranteed.

## 17. MTVD

Mean Time to Validated Defense (`mtvd`): `available`, `validated_scenarios_with_duration`, `validated_scenarios_missing_duration`, `mean_minutes`. Computed **only** from scenarios where `validated_defensive_experience == true` **and** `duration_minutes` is not `null`. `mean_minutes` is the arithmetic mean of exactly those caller-supplied values — never a generated, estimated, or system-clock-derived duration.

## 18. MTVD availability rules

`available = validated_scenarios_with_duration > 0`. When zero scenarios qualify, `available: false` and `mean_minutes: null` — this module never substitutes `stage_count_proxy` (or anything else) for a missing duration.

## 19. Stage-count proxy

`stage_count_proxy`: `available`, `validated_scenario_count`, `mean_stage_count_to_validated_experience` — computed from `len(handoff_stage_results)` for every scenario with `validated_defensive_experience == true`, independent of `mtvd`. Explicitly labeled a **stage-count/workflow-complexity proxy** — never time, never MTVD, never latency, never response duration.

## 20. Context ablation

`ablations.context_enabled`/`ablations.context_disabled` — each scenario grouped by its own `context_mode`. Each group returns `scenario_count`, `validated_defensive_experience_count`, `validated_defensive_experience_rate`, `mean_stage_count`, `mean_duration_minutes`.

## 21. Memory ablation

`ablations.memory_enabled`/`ablations.memory_disabled` — grouped by `memory_mode`, same five-field group contract.

## 22. Governor ablation

`ablations.governor_enabled`/`ablations.governor_disabled` — grouped by `governor_mode`, same five-field group contract.

## 23. Empty-group behavior

When an ablation group's `scenario_count == 0`: `validated_defensive_experience_rate`, `mean_stage_count`, and `mean_duration_minutes` are all `None` — never fabricated as `0`, `0.0`, or any other placeholder. `mean_duration_minutes` is likewise `None` whenever a non-empty group contains zero scenarios with a supplied duration. No causal statement is ever attached to any ablation group.

## 24. Fixed research limitations

`research_limitations` is always exactly these seven codes, in this fixed order, in every result: `OBSERVATIONAL_SUMMARY_ONLY`, `NO_CAUSAL_CLAIM`, `NO_STATISTICAL_SIGNIFICANCE_TEST`, `CALLER_SUPPLIED_DURATION`, `CALLER_SUPPLIED_APPROVAL_STATE`, `RECORDED_STAGE_NOT_EXECUTION_PROOF`, `EVIDENCE_REFERENCE_NOT_AUTHENTICITY_PROOF`. Never shortened, reordered, or omitted because a result "looks good."

## 25. Research CLI

`core/research_evaluation_cli.py`, invoked as `py -m core.research_evaluation_cli`. Exactly 1 operation, `"evaluate"`, via a two-field envelope: `operation`, `experiment`. The CLI validates only top-level envelope shape (JSON parses, is a dict, `operation == "evaluate"`, exact two-key set) — all experiment/scenario-content validation is delegated entirely to `core.research_evaluation`. Output is exactly the core function's own result, `sort_keys=True`, no wrapper — never `{"success": true, "result": ...}`. Exit codes: **0** — any valid evaluation, including one whose `governor_memory_protection.unsafe_reusable_violations` is greater than zero (a normal research observation, never a CLI failure); **2** — envelope violation or a `ResearchEvaluationError` (stderr `RESEARCH_EVALUATION_VALIDATION_FAILED`); **1** — unexpected internal failure (stderr `RESEARCH_EVALUATION_INTERNAL_FAILURE`). No traceback, exception class name, entire experiment payload, or evidence list is ever leaked to stderr.

## 26. `/research-evaluation`

One invocation performs exactly one evaluation. The command passes the caller's complete envelope through unchanged to the CLI — it never generates a synthetic scenario result, never invents a missing duration, never modifies a scenario record, and never automatically runs `/bug-bounty`, `/red-team`, `/blue-team`, `/purple-loop`, `/security-handoff`, `/security-governor`, or `/security-memory` to produce the records it summarizes. It renders every metric as an observed count/rate, explicitly distinct from a causal claim (see the command file's own worked "allowed" vs. "not allowed" phrasing examples), interprets `mtvd`/`stage_count_proxy` without ever substituting one for the other, surfaces `unsafe_reusable_violations` prominently rather than hiding it, and always renders the full, unshortened `research_limitations` list.

## 27. AI Asset Registry

One new asset: `claude_command:research-evaluation`, `provenance.tier: "repository_declared"` — same convention as every other entry. No new `gateway_tool`, `identity_agent`, `claude_subagent`, or `claude_skill` was added — Block 15E is a deterministic local evaluation service with no execution engine and no new governed tool call. Current registry totals: `gateway_tool` 8, `identity_agent` 6, `claude_subagent` 4, `claude_command` **30**, `claude_skill` 1, `mcp_server` 2 — **total 51** (50 before this checkpoint). A direct comparison of actual `.claude/commands/*.md` files against registered `claude_command` assets confirmed exact 1:1 coverage (30/30), with no duplicate asset IDs and no other discrepancy found.

## 28. Determinism

`evaluate_research_experiment` is a single pure computation over its own `experiment` argument alone. The same input always produces byte-identical output (verified via repeated-call equality tests). No network, filesystem, environment-variable, subprocess, system-clock, or randomness access occurs anywhere in `core/research_evaluation.py` or `core/research_evaluation_cli.py`; no UUID or timestamp is ever generated; no Supabase/database, MCP, or LLM/model is ever called; no embedding or vector-database library is used.

## 29. Input immutability

Neither `experiment` nor any nested value within it (`scenario_records`, each scenario's `handoff_stage_results`, `source_evidence_digests`, `final_evidence_references`) is ever mutated by this module. Every returned mapping and list is newly constructed — verified via deep-copy-before/after comparison and a test confirming that mutating the caller's own input after a call never affects an already-returned result.

## 30. Security/research-honesty boundaries

Neither the core module, the CLI, nor the command ever claims: statistical significance, causality, guaranteed security improvement, exploit prevention, remediation success, source-vulnerability validation, autonomous Red execution, continuous Governor monitoring, automatic learning, authenticated approval, authentic evidence, or a generated/fabricated duration. Every output string value is either a fixed vocabulary member, a fixed research-limitation code, or the caller's own `experiment_id` — there is no free-text field anywhere in the output contract through which a stray claim could be introduced.

## 31. Current limitations

`experiment`/scenario records are consumed as plain, duck-typed, caller-supplied mappings — this module never re-derives or independently re-verifies the Block 15B/15C/15C.5/15D computations that produced them; a caller who supplies internally-inconsistent or fabricated scenario data receives metrics computed from that data. There is no cross-session persistence, no audit-trail integration with `core.tamper_evident_audit`, and no automatic linkage back into a running Block 15C case, Block 15C.5 Governor evaluation, or Block 15D memory entry. Only structural consistency between fields that this module itself defines (severity/priority-direction, context/Governor baselines) is checked — no consistency check exists between, say, `memory_experience_status` and `memory_reusable` (deliberately, so that `unsafe_reusable_violations` can be observed rather than silently rejected).

## 32. Research-paper usage

Block 15E now enables future experiments comparing: severity-only prioritization vs. context-aware prioritization (`context_prioritization` metrics + `ablations.context_enabled`/`context_disabled`); memory disabled vs. Validated Security Experience Memory (`memory` metrics + `ablations.memory_enabled`/`memory_disabled`); Governor disabled vs. Governor-enabled policy control (`governor`/`governor_memory_protection` metrics + `ablations.governor_enabled`/`governor_disabled`) — while measuring Governor intervention rate, unsafe reusable-memory violations, Red→Blue revision cycles, evidence preservation, human-review rate, validated defensive-experience rate, MTVD where duration exists, and the stage-count proxy where it does not. **No empirical improvement is claimed by this checkpoint** — these are the measurement primitives a future real experiment would use, not a result.

## 33. Future statistical analysis

Explicitly deferred until real experiment datasets and appropriate sample sizes exist: p-values, confidence intervals, significance tests, effect-size claims, and causal inference of any kind. `research_limitations`'s `NO_STATISTICAL_SIGNIFICANCE_TEST` and `NO_CAUSAL_CLAIM` codes exist precisely to keep this boundary visible in every result this module can ever produce.

## 35. Block 16 handoff

Block 15E deliberately stops at a pure, local, deterministic evaluation service: an experiment format, a metrics core, a thin CLI, and a supervisory command — with no persistence, no statistics engine, and no execution capability. Nothing in this checkpoint runs a real experiment, writes a research dataset, or draws a conclusion; it only defines and validates the measurement contract a future block (or an external research process) could use to record and later evaluate real ThreatTrace scenario batches. Any future work involving experiment persistence, an actual statistical-analysis layer, or automated experiment orchestration is explicitly out of scope for Block 15E and is not started here.
